# Protocol detail

Per-step detail for `SKILL.md` `## Protocol`. The SKILL carries the rule; this file carries the mechanics and the observed incident behind each one. Consult it when executing the step it belongs to, not before.

Every rule here is subordinate to the SKILL's `## Goal contract` and `## Finding severity floor`. Where a paragraph below reads as licence to widen a wave, the floor wins.

## Step 1 — executor-writability pre-flight

Before queueing waves that write a given directory, confirm `the-looper` (a SUBAGENT) can actually write there. Some projects gate subagent writes to UI dirs (a `.tsx`/`components/` write-gate, a permission allowlist) — invisible to a main-agent check, since the gate is subagent-scoped. A queue full of waves the executor cannot write turns every wave into an unclearable escalation (the specialist that would "clear" it has no Write tool either — see `## Step 2b`). Probe once, or read project memory for a known gate; if the executor is gated out of the target dir, surface to the user BEFORE burning a pilot dispatch, and consider a non-gated target or a main-agent-build fallback.

**A session-marker gate false-negatives on a COLD probe — probe AFTER its clearing action, not before.** Some UI write-gates are PreToolUse hooks that DENY until a session marker exists, dropped the first time a clearing specialist runs (`accessibility-agents`' `a11y-enforce-edit.sh` denies `.tsx`/`components/` writes until `/tmp/a11y-reviewed-<SESSION_ID>` exists, set by a PostToolUse hook when `accessibility-lead` runs once; subagents share the parent SESSION_ID, so the orchestrator's per-wave a11y-lead brief clears it session-wide). A probe in a virgin session — before any a11y-lead consult — ALWAYS blocks; reading that as "executor can't write here" is a false negative that escalates a non-existent blocker (observed: a full round-trip on the theme-editor run). For a marker-scoped gate: run the clearing specialist (or set the marker) FIRST, THEN probe — and since the per-wave a11y-lead brief sets the marker anyway, a UI run whose waves each carry a pre-build a11y-lead gate needs no separate executor escalation. Only escalate when the gate has NO clearing action the orchestrator can trigger.

## Step 1 — the already-vetted-plan exception

A goal that arrives as an already-vetted, user-approved implementation plan may skip `looper-scope`'s decomposition, but not its validation. When the goal is not a raw ask but the output of a prior Plan-Mode cycle (research → plan agent → `AskUserQuestion` rounds → user `ExitPlanMode` approval), that cycle already performed scope's decomposition job — often with more rigor, since it verified load-bearing claims against the actual source and resolved open design decisions with the user directly. Re-running `looper-scope` on a terser restatement of an already-decided goal risks it inventing a DIFFERENT decomposition that silently overrides decisions the user already approved — an authority violation in the opposite direction from the one scope guards against.

In this case build the wave queue directly from the plan's own wave breakdown, but still perform scope's mechanical validation by hand: the goal contract (`SKILL.md` `## Goal contract` — the plan's own stated asks ARE the contract, transcribe them), wave queue non-empty, executor-writability pre-flight, and `required-not-loopable` capture. Record the substitution and which checks were kept in `run-state.json` under `nonbeliever.notes` so a resume or audit can see the queue's real provenance. Narrow: it applies only to a plan that went through real user back-and-forth, not to a self-authored plan the orchestrator wrote in the same turn without a check-in.

## Step 2a — stale-candidate pre-check

Scope builds the queue ONCE up front; by a later wave an earlier wave may have already renamed, deleted, or fixed what this wave targets. A full dispatch is expensive — don't spend one to hand back "file gone." Before dispatching, run a cheap glob/grep: do the target files still exist, and still exhibit the thing this wave addresses? Stale → mark the queue item `status: "skipped-stale"` with the reason, log it (`gates.jsonl`, `kind: "stale-skip"`), advance. Do NOT escalate — a stale candidate is already-handled work, not a blocker. Skip only when the target is provably gone or already-satisfied, NOT when a path merely moved (a moved target is a re-point, still a live wave). A stale-skip is NOT a no-progress event — no `the-looper` ran, so it never touches `consecutive_no_progress`.

## Step 2a — brief authoring

**PR + push directives.** Every wave brief carries two SEPARATE flags; never bundle them into one "No PR, nothing flipped to ready" phrase — that conflation collapses two different actions and orphaned PR creation in a real run (`pr-lifecycle.md`).

- `pr:` — `create-on-wave-1` (default on a fresh multi-wave branch) | `existing #N` (every wave once the PR exists) | `skip` (explicit, rare — throwaway spike). "Don't flip to ready-for-review" is NOT a `pr:` value; the draft is still created.
- `target.push: true` — on EVERY wave of an orchestrated run; the orchestrator owns push timing and its default-off is for standalone use, so it must set this explicitly.

**Standing quality instructions that pre-empt the most common corrective wave.** Code built to a cleared pre-build contract ships _correct_ on the first build; the gaps that still fire are overwhelmingly **unearned-comment**, **untested-invariant**, **stale-docstring**, **orphaned-prose**, and **unverified-duplicate-contract** — all cheaper to prevent in the originating wave than to carry to the cleanup batch. They are carried verbatim in the standing-brief template `SKILL.md` `## Protocol` 2a names, and every runtime-code wave brief includes it (the deletion-sweep line fires only on deletion/removal waves, the duplicate-contract line only on doc/example waves, the falsified-claim line only when a wave discovers an already-shipped claim is false, the ambient-condition line only when a brief sends an agent to determine what an ambient/override value does). These are prevention, not new scope — they cover the wave's OWN change, and for a deletion the references its own removal orphaned.

Unearned-comment leads that list on purpose. It is the one gap the cleanup batch has consistently failed to close, because every downstream pass reads a comment as content to preserve rather than a line that had to earn its place — so the only reliable fix is not writing it. The instruction pairs a rule with a mechanical check (`~/.claude/scripts/doc-bloat-scan.sh` over the wave's own touched files), since prose-only warnings have already been observed not to hold.

**A technical claim in a brief is one the orchestrator is MAKING, not one it is quoting — check it before writing it, or mark it unverified.** An assertion about the tree offered as justification — what is installed, what already exists to reuse, what a check does or doesn't constrain — hands the executor a premise, and a premise is BUILT on, not checked. Give each one the cheap check that settles it (a grep, an `npm ls`, opening the named file and reading its imports), or write it in as `unverified — confirm before implementing`. Distinct from **unverified-duplicate-contract** above, which binds the WAVE, not the orchestrator. Observed: two consecutive briefs in one run asserted three false claims — a dependency claimed installed that `npm ls` showed absent, a "harness to reuse" that touched neither technology claimed for it and served pre-rendered HTML over bare `node:http`, and a claim that a size check spared devDependencies when it constrained both dependency maps in the same loop. The wave caught all three, so nothing shipped wrong, which is exactly why "the executor will catch it" is not the mitigation: the detour is the cost and it is paid per dispatch, while the check that prevents it is seconds at authoring time.

**Gate authoring on a deletion wave — point the specialist at the CONSUMERS, not just the deletion site.** A pre-build gate whose brief names only the deleted/edited files gives the specialist no line of sight to a regression _outside_ that set. On a feature-removal wave the gate brief must additionally name the deleted feature's consumers, callers, and adjacent user-facing copy. Observed: an a11y-lead gate cleared the Try-It deletion cleanly but the WelcomePanel content regression (stale "hit Send" instructions) escaped it — WelcomePanel sat outside the gate's fileset.

**EXTRACTION / SPLIT / god-file-refactor waves — make the per-OUTPUT-file ceiling this wave's acceptance criterion, and demand the counts.** The no-god-files rule already binds the executor and the crew, so bloat that merely relocates is a compliance gap, not a missing rule. What the brief adds is scope and evidence: the ceiling applies to EVERY resulting file, and the executor must state each output file's code-LOC count in its hand-back. Without that reported count the size signal silently re-trips on the NEW file — invisible to type-check and tests. Take the threshold from the target repo's CLAUDE.md exactly as `looper-build` does; do NOT hardcode a number. Observed: a wave thinned a 229-line hook to 70 but created a 138-code-LOC extracted module.

Note the altitude: a per-output-file ceiling is an acceptance criterion on an extraction wave, where shrinking files IS the goal contract. On any other wave a LOC finding is below the floor and batches.

## Step 2b — gate classification

- **Design gate** (a judgment a specialist supplies: palette/contrast values, threat model, ARIA contract). A specialist CLEARS it by producing the missing judgment. Route to the named specialist.
- **Tooling gate** (a write-block / permission denial / missing credential the executor hit). A specialist CANNOT clear it — the review crew (`the-diamantaire`, `the-stickler`) run `Bash, Read` only and `accessibility-lead` is likewise read/review-scoped: **no Write tool** among them, so invoking one to "clear" a write-gate accomplishes nothing. A tooling gate is a USER decision (exempt the executor, change the target, or accept a main-agent-build fallback). Escalate to the user immediately; do NOT round-trip a specialist that can't resolve it. Log the gate `ran: false` with the tooling reason.

For a design gate: invoke the named specialist via Task tool with the input `the-looper` specified, append its output to the brief as `gate outputs`, and re-dispatch — the executor sees `gate outputs` populated, skips plan, resumes at build. Record each pre-build gate in `gates.jsonl` (`rails.md` `## Gate artifacts`): which specialist, ran-vs-unavailable, verdict. A gate the executor _requested_ but the orchestrator could not invoke (no Task tool) is logged `available: false` — never recorded as passed. Same specialist gate requested twice for the same wave → STOP, escalate to user.

**Pre-mandated gates fire up-front, not via a round-trip.** Two sources tag a wave for an up-front gate: `looper-scope` (explicit queue tag) and the **UI-glob detector** the orchestrator runs over each wave's candidate files before dispatch. The UI-glob mirrors `looper-plan`'s `### UI-touching waves always tag` exactly (`*.tsx`/`*.jsx`/`*.vue`/`*.svelte`/`*.html`, server templates `*.leaf`/`*.ejs`/`*.erb`/`*.hbs`/Jinja, styling `*.css`/`*.scss`/Tailwind/token files) — any match makes the wave UI-touching and mandates `accessibility-lead`. Detecting it at dispatch time matters because the accessibility hook fires only on the parent prompt, never inside the executor subagent — the orchestrator is the only actor that can guarantee the gate. When tagged, invoke the specialist BEFORE dispatching and ship the contract as `gate outputs` in the first brief. Do NOT dispatch only to have the plan re-discover the known gate; the reactive path is for gates the plan finds that scope did NOT foresee. If the specialist returns open design decisions that are implementation specifics inside the user's already-stated design (clip strategy, control reuse, caption copy), resolve them on the specialist's recommended defaults. A decision that re-opens scope still goes to the user.

**Behavior-neutral cleanup waves are the one carve-out to the up-front a11y gate — confirm post-build instead.** A cleanup wave whose ENTIRE diff is provably non-behavioral (dead-code removal, comment fixes, an unreachable-predicate alignment leaving rendered output byte-identical) adds no new UI behavior or a11y surface — the live behavior was already gated when it shipped. Skip the up-front gate; instead re-run `the-auditor` on the diff POST-build to confirm byte-identical rendered a11y output. Holds ONLY when the wave proves byte-identical output (tests green AND the diff changes no rendered attribute, role, name, or computed style). The moment a "cleanup" wave touches real markup or behavior it is a normal UI wave and the up-front gate is mandatory again. Do NOT stretch this to a wave that "mostly" doesn't change behavior.

## Step 2b-retry — stuck-wave retry-from-scratch

Before bubbling a **retryable** stop up to Step 4, attempt EXACTLY ONE fresh-context re-dispatch — a stuck agent escapes more often from a clean restart than from more turns on a rotted context (ComPilot's multi-run finding). "From scratch" means fresh CONTEXT, NOT a freshly-improvised plan.

**Resume is not retry — classify before you re-dispatch.** A wave that died with NO hand-back (session limit, crash, a killed session) did not fail; it was interrupted. That is a RESUME: re-dispatch it plainly and `the-looper` picks up at its next unfinished journaled step. Only a wave that handed back a retryable STOP is a RETRY, and a retry never resumes — its brief's `prior attempt failed:` note is also what tells the executor to open a fresh journal segment instead of continuing the dead one (`agents/the-looper.md` `## Step journal`). Do NOT spend a retry, or its `wave_retries` count, on an interruption.

**Retryable** (non-deterministic — a fresh attempt can plausibly differ): `verify fails twice` on the same root cause; review verdict `rethink`; a wave that tripped `consecutive_no_progress`.

**NOT retryable** (deterministic — a retry hits the same wall and burns a dispatch): tooling gate / write-block / permission denial, nonbeliever STOP, scope refusal, a budget governor rail, or a design `gate needed pre-build`. These bubble up immediately.

Mechanics:

1. **Fresh agent, not a resume.** Re-dispatch with NEW context — drop the rotted context and failed path.
2. **Directed, not blind — revert to the next ranked plan first.** The retry brief carries a `prior attempt failed:` note (the failure mode in one line). The retry FIRST reverts to the next-highest-ranked alternate the wave's `looper-plan` emitted, if one exists — vetted against the same constraints while research context was fresh, so the shot is spent on a pre-vetted approach, not a cold guess (MapCoder, ACL 2024). Only when the plan emitted NO ranked alternate does the retry improvise from the failure signal. Either way pass the note.
3. **One shot.** Best-of-2. A second stuck hand-back on the SAME wave bubbles to Step 4 and escalates to the user.
4. **Log it.** Append a `kind: "wave-retry"` event to `gates.jsonl`. A retry the orchestrator could not dispatch logs `ran: false`.
5. **Counters.** A retry increments `total_waves` and `wave_retries` (never reset). It does NOT increment `corrective_waves` — those are floor-gated fix waves, a different cause. A retry that ships net-new work resets `consecutive_no_progress`; one that fails again counts toward it.

## Step 2b-flags — triage cross-file flags before advancing

A wave can SHIP clean yet hand back a `flag` naming a **cross-file incompleteness** — a reference (to a field, section, contract, channel in ANOTHER file) that doesn't exist yet, or a sibling file needing a matching change. "X references Y, but Y isn't defined" is a known defect the moment reported. On every shipped wave, read the hand-back `flags` before dispatching the next:

- **Cross-file incompleteness** (a dangling reference the wave created) → if a later queued wave touches the named file, fold the fix into its brief; otherwise append to `cleanup_batch`. It is a defect of this run's own diff, so it is admissible — but it is not automatically above the floor, and a dangling doc reference is not a reason to spend a corrective wave.
- **Self-caused behavior-neutral debris** (dead code the wave's OWN change orphaned — an overridden CSS rule, an unused param after a deleted caller) → clean it INSIDE the creating wave, do NOT flag-and-defer. Pre-authorize `the-looper` in the brief to delete debris its own change orphans. A tight "implement the contract, nothing beyond" brief is what produced the flag-and-defer, so the brief must explicitly carve out "AND delete any dead code your change orphans" as in-scope, distinct from the no-scope-creep rule.
- **Out-of-scope observation** (a pre-existing issue the wave noticed but didn't cause) → capture for a future scope run; never actioned mid-run, and never a `cleanup_batch` item. The run did not cause it.

Test is causation + reachability: did THIS wave create the dangling reference (or orphan the dead code), and can a queued wave — or the creating wave itself — close it?

**A flag that an already-shipped FACTUAL CLAIM is false is none of the three above — do not force it into cross-file incompleteness.** "X references Y, but Y isn't defined" is a dangling reference; "we already told people X, and X is wrong" is a falsified claim, and folding it into cross-file incompleteness inherits a LATER wave's file scope, which never reaches the other places the same false wording lives (source comments, the CHANGELOG, emitted `.d.ts`, the PR body). `templates/wave-brief-standing.md`'s falsified-claim standing line is prevention — it fires in the wave that DISCOVERS the falsehood, in the same brief, before hand-back. **If a flag reaches this section anyway (prevention missed it, or the discovering wave wasn't briefed with the standing line), dispatch a DEDICATED wave whose brief is that standing line, scoped to the WHOLE repo.** Never fold it into another wave's narrower file scope and never park it in `cleanup_batch` — a shipped falsehood is misleading readers now, not a batchable nit, and both of those inherit exactly the scope-shrinking that let the falsehood's other copies survive in the first place.

## Step 3 — crew pass mechanics

**Every crew-agent prompt must explicitly state "report findings only, do not edit any files".** Several crew agent definitions are dual-purpose (their own system prompt says "audit or fix", "refactor and clean up") because they're also invoked standalone. Inside a crew pass they must stay read-only — a crew member that edits the working tree bypasses the wave/commit/verify discipline entirely (no test run, no review, nothing in `gates.jsonl` beyond a verdict line). Observed: `the-chronicler`, prompted only to "review... report... with file:line," made a direct uncommitted edit. Two guardrails: (1) every crew prompt gets the explicit no-edit line; (2) run `git status --porcelain` immediately after every crew pass returns — a non-empty result means a crew member edited files directly, and that pending diff must be routed through a proper `the-looper` micro-wave before proceeding, never committed directly by the orchestrator and never silently left uncommitted.

**Diff base.** Each agent gets the cumulative diff since the last crew pass, or for the final crew since the run's own first wave commit. Scope to THIS run's commits, NOT blindly `main..HEAD`: a branch handed over mid-flight already carries unrelated pre-run work that would drown the crew in out-of-scope findings. Derive the base as the parent of wave 1's commit (`git diff <wave1>^..HEAD`); only a branch forked fresh for this run makes that equal `main..HEAD`. The same base feeds the structured-recap refresh (`pr-lifecycle.md`) — derive it once, reuse it.

**Independent re-check of a mechanically-checkable fix claim.** A corrective wave can ship a false "fixed" claim. Observed: a corrective reported "`npm run format` clean" as proof it fixed a formatting finding, but the project's `format` script glob never covered `.css` — the command silently no-oped and exited 0. For any fix claim resting on a mechanically-checkable command (format/lint/build exit code, a specific file's lint-clean status), re-run that EXACT check independently (`npx prettier --check <file>`, not just trust `npm run format`'s exit code) before advancing. Cheap, and it does not depend on a crew pass to catch.

**Re-crew scope follows the corrective diff, not ceremony.** Re-run the agents whose findings the fix targeted, plus any whose domain the corrective diff actually touched. An agent that was clean AND whose domain the fix never entered need not re-run — a docs+test corrective that only deletes a dead attribute doesn't re-summon the correctness/a11y reviewers, provided the behavior-unchanged claim is verified. State which agents you re-ran and why; do NOT silently drop a clean agent whose domain the fix DID touch. The re-crew is terminal and answers CLEARED / NOT-CLEARED only (`SKILL.md` `## Corrective budget`).

**Report all seven.** The crew summary in any report enumerates ALL SEVEN agents by name with each verdict — ran-and-clean, ran-and-found, or not-run-this-pass. Listing only the agents that found something silently drops the rest; a reader can't tell "ran, clean" from "never ran" (the-improver was dropped from a clean report once exactly this way). Under a domain-matched interim pass most agents will read `not run this pass — domain not touched`, which is a report line, not an omission.

**A crew agent sent to determine what an ambient condition, environment variable, or override value ACTUALLY does needs the axis named, not just the value.** Same rule as `templates/wave-brief-standing.md`'s ambient-condition standing line — a single-ambient probe confounds hypotheses that predict identical output under the one condition tested. State the axis to vary (headless vs. interactive, this machine vs. another) in the prompt and require the full table back, not a verdict.
